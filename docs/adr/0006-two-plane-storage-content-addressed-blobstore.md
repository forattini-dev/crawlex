# Two-plane storage: RedDB index/memory + content-addressed BlobStore

`crawlex` stored page bodies inline in whichever storage backend was selected. In the RedDB backend (`storage::reddb`) that inline write is capped: `REDDB_INLINE_BODY_LIMIT_BYTES = 384 KiB` and `REDDB_INLINE_HTML_LIMIT_BYTES = 512 KiB`, because a RedDB document insert passes through the query parser and hits `max_input_bytes` at ~1 MiB. Bodies larger than the cap are truncated and flagged `truncated: true`. That is a silent coverage ceiling on exactly the pages the code comments call out (large pharmacy / SPA pages), and it contradicts the project's maximum-discovery default. Separately, there was no cross-URL content dedup — the video's "don't re-parse content already parsed under another URL" — so two URLs with identical content were both fetched, parsed, and stored.

Investigating the current RedDB (`/home/cyber/Work/reddb.io/reddb`) settled the direction:

- RedDB's `BlobCache` (`write_native_blob_chain`, page-aligned chunk chains, L1/L2 + sweeper) is a **server-internal result cache**, not a client-facing object store. It is for caching query results, not for durable application blobs.
- RedDB's own doctrine is explicit (`docs/query/ai-policy.md`): it "does not introduce a binary/blob type" for media — large binaries are **referenced by URL/URI**, not stored. A `Blob` column exists for small binary only.

So RedDB is deliberately not the place for multi-hundred-KiB HTML. The bytes belong in a blob store; RedDB holds the reference. This splits storage into two planes:

- **Index / memory plane — RedDB.** Frontier (durable queue + dead-letter), the Seen-set (last-crawled TTL, ADR-0005), the link graph (`link_edges`), host intel (`host_tech`, `host_facts`, tech fingerprints), session / antibot state, crawl stats and attempts, telemetry — and the **pointer + metadata** for each stored body. This plane is where RedDB's newer strengths pay off (native graph, vector `SEARCH SIMILAR`, time-series / hypertables, queues); those are earmarked for the stealth-memory and coverage tracks, not this ADR.
- **Byte plane — a content-addressed `BlobStore`.** Page bodies and artifacts, keyed by `cas:<content-hash>`. Pluggable backend, all shipped in this slice: `fs` (default, zero-config), `s3`, `r2`. The RedDB storage backend stops inline-truncating; it writes bytes through the `BlobStore` and records only the `cas:` pointer + size/metadata in RedDB. `filesystem` and `sqlite` backends already emit `cas:<sha256>` pointers; page-body storage is unified onto the same content-addressed path.

Decision: adopt the two-plane split with a pluggable, content-addressed `BlobStore` trait (`fs` default + concrete `s3` + `r2`). The dedup key **is** the CAS key: the **Content identity** — a hash over the *normalised text* (post `extract::html_clean`, robust to CSRF tokens, timestamps, session ids that make raw-HTML hashes differ trivially), not over raw bytes. Dedup is **non-destructive**: identical content is stored once, but the second URL and its graph edge are still recorded, so discovery is never lost (honours the maximum-discovery default). The same content-hash also drives the same-URL TTL refresh short-circuit from ADR-0005: an unchanged Content identity on a stale-by-TTL re-crawl bumps `last_crawled` without a re-store, composing with `cache_validator`'s 304 / ETag / Last-Modified path.

Consequences and the consistency rule: there are now two sources of truth (RedDB index, BlobStore bytes), so writes are ordered **bytes first, pointer second** — commit the blob, obtain its `cas:` handle, then write the RedDB pointer. A crash between the two leaves an orphan blob, never a dangling pointer; orphan reclamation by content-hash refcount is future work (a GC/sweeper pass), acceptable because an orphan blob is inert. `s3` / `r2` additionally give remote durability and let a full crawl's bytes outlive the local machine.

Alternatives rejected: chunk large bodies into RedDB (against RedDB's own reference-by-URI doctrine, and its blob chain is an internal cache, not durable client storage); `fs`-only (does not meet the requirement to run against `s3` / `r2` now); raw-HTML hashing for the dedup key (too brittle — trivial per-request tokens defeat it).
